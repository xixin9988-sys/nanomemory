# NanoMemory Vector Memory v1 — Threat Model

Status: **proposed design review; controls are not implemented merely by being listed here**  
Date: 2026-11-27

## 1. Assets

- Canonical memory text and associated attachments.
- Embeddings and ANN indexes.
- Tenant, subject, collection and session ownership metadata.
- Provenance, trust labels, lifecycle state and correction history.
- Provider credentials and database credentials.
- Retrieval traces, prompts, tool outputs, feedback and usage records.
- Backups, exports, migration checkpoints and audit events.

## 2. Principals and trust boundaries

- End user: untrusted input; identity is established by the application authentication layer.
- Calling application / BFF: trusted only after service authentication and scope validation.
- NanoMemory API: validates request contracts and maps trusted identity to repositories.
- mem-guard: policy compiler and trust/governance decision source; not an identity provider.
- PostgreSQL: system of record; database roles, RLS and partition boundaries enforce access.
- Embedding / LLM provider: external processor; receives only the minimum content needed for the operation.
- Operator: privileged access, audited separately from end-user access.
- Backup / export destination: separate security boundary with explicit access and retention.

## 3. Threat scenarios

### T-01 — Cross-tenant or cross-user vector retrieval

Threat: a query returns another principal's memory because a global ANN index is searched and results are filtered only after retrieval.

Required controls:
- resolve security-domain grants from verified identity before retrieval;
- partition the ANN index by security domain and search only authorized partitions;
- RLS and SQL predicates as defence in depth;
- exact filtered search or deny when fine-grained ACLs do not map to the partition boundary;
- EXPLAIN-plan and adversarial tests proving partition pruning and zero foreign candidate IDs.

### T-02 — Prompt injection stored as memory

Threat: untrusted document or user content is retrieved and treated as instructions.

Required controls:
- preserve source type and provenance;
- keep memory in an explicitly untrusted context block;
- never let memory content alter tool permissions or identity;
- quarantine suspicious content and require an explicit review transition;
- test malicious instructions in both retrieved text and metadata.

### T-03 — Model inference becomes a user fact

Threat: generated text is stored as verified truth without evidence.

Required controls:
- model-originated records default to pending_confirmation or quarantine;
- deterministic validation controls admission;
- model confidence cannot raise trust;
- provenance points to source and run identifiers;
- activation is an explicit, audited transition.

### T-04 — Embedding model or dimension mismatch

Threat: query vectors generated by one model/revision/dimension are compared with stored vectors from another incompatible profile.

Required controls:
- versioned embedding profiles;
- validate dimensions and model revision at startup and write time;
- one active profile/dimension per v1 deployment;
- blue-green backfill and evaluation before profile switch;
- stale/missing embeddings are visible as index state, not silently mixed.

### T-05 — Data loss during JSON migration or re-indexing

Threat: an interrupted import or embedding job drops records or changes provenance/status.

Required controls:
- dry run, stable migration ID and checkpoints;
- idempotent operations;
- source/target count and per-record hash reconciliation;
- source backup retained until restore drill passes;
- embedding failures do not delete canonical records;
- compensating rollback with immutable audit events.

### T-06 — Credential exposure

Threat: provider or database secrets leak through browser assets, logs, errors, exports or repository history.

Required controls:
- secrets only on server side;
- secret scanning in CI;
- runtime secret injection;
- redaction in all logging paths;
- no secret values in health responses or error details;
- rotate compromised credentials.

### T-07 — Denial of service and cost exhaustion

Threat: long prompts, high-dimensional embedding batches, unbounded concurrent model requests or repeated recall exhaust compute and provider budget.

Required controls:
- request/body limits and per-principal rate limits;
- token, batch, timeout and concurrency budgets;
- per-tenant quotas and cost records;
- bounded retries with jitter and circuit breaking;
- cancellation and backpressure for embedding queues.

### T-08 — Audit and telemetry become a data leak

Threat: logs capture raw queries, memory content, PII or secrets and are retained indefinitely.

Required controls:
- metadata-only operational traces by default;
- explicit opt-in for content traces;
- field-level encryption, restricted audit access and retention policy;
- access to trace content is itself audited;
- export redaction and deletion policy are documented.

### T-09 — Unauthorized restore or export

Threat: an attacker or operator restores stale content, exports all memories or permanently deletes records.

Required controls:
- separate admin capability;
- step-up confirmation for destructive actions;
- signed/hashed backup manifests;
- pre-restore snapshot and rollback;
- audit actor, reason, request ID and before/after versions.

## 4. Abuse cases to include in evaluation

- Same semantic content in two tenants and two private users.
- A user with only one collection grant asks a query matching an inaccessible collection.
- A malicious memory says to reveal keys or call a dangerous tool.
- A model inference contradicts a verified user statement.
- An embedding provider returns a wrong dimension, NaN or malformed vector.
- A job retries after commit and must not create duplicates.
- A migration is interrupted after partial embedding backfill.
- A prompt includes a very large input intended to exhaust tokens or memory.
- A user requests a non-existent fact and the system must abstain.
- A trace/export request is made by an unauthorized principal.

## 5. Residual risks and release decision

- HNSW is approximate and filtered recall/latency must be benchmarked under real tenant and collection skew.
- Security-domain partition count may create planning and maintenance overhead; load testing is required.
- External embedding providers receive source text unless a local embedding model is configured.
- Local administrators and database superusers remain privileged trust principals.
- RLS can be bypassed by superusers, BYPASSRLS roles and normally table owners unless FORCE ROW LEVEL SECURITY is used; deployment roles must be designed accordingly.

No public multi-tenant deployment should be approved until the cross-domain retrieval, RLS role, backup/restore, secret and abuse-case gates pass in CI and staging.
